# Исследование и продуктовые решения

## Персоны
| Персона | Контекст | Главная задача | Боль |
|---|---|---|---|
| **Анна, ИП, кофейня** (оборот 14 млн/год) | Сама ведёт бизнес, нет финансового образования | Быстро закупить товар к сезону | Не понимает, какой продукт выбрать; боится отказа и «чёрного ящика» |
| **Виктор, директор ООО, опт** (60 млн/год) | Есть действующие кредиты | Закрыть кассовый разрыв | Получает отказ без объяснений, хотя готов на другие условия |
| **Ольга, главный бухгалтер** | Готовит документы за директора | Собрать заявку без ошибок | Повторный ввод данных, запросы документов по почте/телефону |
| **Дмитрий, директор производства** | Крупный инвест-проект с залогом | Финансирование оборудования | Долгое рассмотрение, непонятно на каком этапе заявка |
| **Елена, кредитный аналитик (банк)** | Очередь заявок | Быстро принять обоснованное решение | Данные разбросаны по системам, рутинные проверки вручную |

## Jobs To Be Done
- *Когда* у меня кассовый разрыв, *я хочу* за несколько минут понять, сколько мне дадут и какой будет платёж, *чтобы* не сорвать закупку.
- *Когда* банку не хватает данных, *я хочу* видеть конкретный список в кабинете, *чтобы* не переписываться и не ждать звонков.
- *Когда* мне не могут одобрить запрошенное, *я хочу* получить альтернативу и понятные причины, *чтобы* решить, подходят ли мне другие условия.
- *Когда* заявка нестандартная, *я (аналитик) хочу* видеть в одном экране анкету, все проверки и разбор скоринга, *чтобы* решить без поиска данных по системам.

## Боль → решение в продукте
| Боль | Решение | Где |
|---|---|---|
| Не понимаю, какой продукт выбрать | Мастер «от задачи», 5 продуктов с платежом и шансом одобрения | `/new`, `POST /catalog/recommend` |
| Повторный ввод данных | Реквизиты из профиля и ЕГРЮЛ, финансы из оборотов по счёту, распознавание отчётности | Мастер, `_extract()` |
| «Чёрный ящик» статуса | Прогресс из 6 этапов, обновление в реальном времени, пояснение каждого статуса | SSE `/stream` |
| Запросы документов вне продукта | Задачи в кабинете с загрузкой файла; повторная отправка в один клик | `NEEDS_INFO` |
| Отказ без причин | Причины + рекомендации, разбор «что помогло / помешало» | Карточка заявки |
| Бинарное «да/нет» | Встречное предложение: больший срок → меньшая сумма → другой продукт | `credit.decide` |
| Бухгалтер не может подписать | Роль без права подписи: оформляет, подписывает директор | `can_sign` |
| Аналитику не хватает контекста | Единая карточка: анкета, сырые ответы источников, факторы, аудит, чат | `/bank/applications/:id` |

## Приоритизация (MoSCoW)
- **Must** — сквозной путь (подбор → заявка → проверки → решение → подписание → выдача), машина состояний, 4 исхода решения, рабочее место аналитика, персональная лента, моки интеграций, Docker, документация.
- **Should** — эскалация по полномочиям, чат с банком, ассистент, симулятор сбоев, аналитика воронки.
- **Could** — LLM-ассистент на open-weights, распознавание документов.
- **Won't (в MVP)** — реальная ЭП и платежи, реальные внешние API, сопровождение кредита после выдачи, ML-скоринг на реальных данных, мобильное приложение.

## Почему такой MVP
Кейс просит не воспроизводить весь банковский процесс. Мы взяли **минимальный сквозной путь**, но сделали каждый шаг настоящим: данные сохраняются, статусы двигаются асинхронным конвейером, решение воспроизводимо. Всё, что требует реальных систем банка (ЭП, платежи, БКИ), смоделировано с сохранением контракта и смысла интеграции.
