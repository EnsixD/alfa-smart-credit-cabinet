# План решения кейса «Умный кредитный кабинет предпринимателя» (Альфа-Хак 2026)

## 0. Суть кейса в одном абзаце

Нужен **работающий веб-прототип цифрового кредитного конвейера для МСБ**: клиент (собственник, директор, бухгалтер и т.п., без банковской экспертизы) проходит путь *«потребность → выбор продукта → заявка → проверки → решение → оформление → (симуляция) выдача»*, а банк в том же продукте видит и обрабатывает заявку (автоматические проверки + андеррайтер). Всё автономно (моки вместо БКИ/ЕГРЮЛ/ФНС), на синтетике, в Docker, без платных API, LLM — только open-weights. Плюс явное требование демо: **персонализированная новостная лента клиента**.

## 1. Исследование (день 1, ~10% времени)

**Цель:** показать связь «потребность → сценарий → фича» (жюри это прямо оценивает).

1. **Персоны** (3 шт.):
   - *ИП-микро* (кофейня, оборот 5–15 млн/год): нужен быстрый оборотный кредит/овердрафт, нет времени, не понимает терминов.
   - *ООО-малый* (производство, 100–400 млн): инвестиционный кредит на оборудование, есть залог, участвует бухгалтер/финдир.
   - *Бухгалтер/уполномоченный сотрудник*: собирает документы, заполняет заявку от имени компании, ему важна полнота и статус.
2. **JTBD** (по 2–3 на персону), например: «Когда у меня кассовый разрыв, я хочу быстро понять, сколько мне дадут и на каких условиях, чтобы не сорвать закупку».
3. **Боли** → **решения** (таблица): непонимание продукта → подбор по цели; повторный ввод → автозаполнение по ИНН; «чёрный ящик» статуса → таймлайн + объяснение; отказ без причины → объяснимое решение + контрпредложение; запрос доп. документов вне продукта → in-app задачи.
4. **Банковская сторона:** андеррайтер — нужна сводка рисков в одном экране, автоматизация рутины, аудит действий.
5. **CustDev-lite:** 5–7 коротких интервью со знакомыми ИП/бухгалтерами (или анализ отзывов о банках на banki.ru) — зафиксировать цитаты.
6. **Приоритизация:** User story map + **MoSCoW** (и RICE для спорных фич). Результат — явный список «что в MVP и почему».

## 2. Модель кредитного процесса

### Границы
От «появилась потребность» до «деньги условно зачислены / отказ / клиент отказался». Вне границ: сопровождение кредита после выдачи (только график платежей как витрина), реальная ЭП, реальные платежи.

### Участники (роли)
- **Клиент** (CLIENT_OWNER, CLIENT_DELEGATE — с ограниченными правами, напр. не может подписывать)
- **Система** (автопроверки, скоринг, decision engine)
- **Андеррайтер / кредитный аналитик** (UNDERWRITER)
- **Кредитный комитет/руководитель** (опц., для сумм выше лимита — APPROVER)
- **Администратор** (настройка продуктов/правил)

### Этапы и статусы (state machine)

```
DRAFT ──submit──▶ SUBMITTED ──▶ DATA_CHECK ──fail──▶ NEEDS_INFO ──client upd──▶ DATA_CHECK
                                   │ok
                                   ▼
                              ENRICHMENT (ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ, внутренние данные)
                                   ▼
                               SCORING
                                   ▼
                           DECISION_ENGINE
             ┌──────────────┬──────┴────────┬──────────────┐
             ▼              ▼               ▼              ▼
       AUTO_APPROVED   MANUAL_REVIEW   COUNTER_OFFER    REJECTED
             │      (андеррайтер:approve/ │ (иная сумма/срок/продукт)
             │       reject/counter/      │
             │       request_info)        │
             ▼                            ▼
       OFFER_ISSUED ◀── client accepts ───┘   (client declines → CANCELLED_BY_CLIENT)
             ▼
       DOCUMENTS_SIGNING (симуляция ПЭП/кода)
             ▼
       DISBURSED (симуляция зачисления)  → CLOSED
```
Плюс `CANCELLED_BY_CLIENT` из любого не-финального статуса, `EXPIRED` для оферты/NEEDS_INFO по таймауту.

### Данные на каждом этапе
- Заявка: продукт, сумма, срок, цель, залог/поручительство (если требуется продуктом).
- Компания: ИНН, ОГРН, ОКВЭД, дата регистрации, адрес, руководитель, учредители (автозаполнение из мока ЕГРЮЛ).
- Финансы: выручка, расходы, текущие обязательства, обороты по счёту (синтетика «внутренние данные банка»).
- Документы: выписка, бух. отчётность, документы по залогу (загрузка + распознавание — опц.).
- Результаты проверок: каждая — `{source, status, payload, checked_at}`.

Артефакты: `docs/process.md`, BPMN (draw.io/bpmn.io), state diagram (Mermaid/PlantUML).

## 3. Архитектура

### Стек (рекомендация)
- **Backend:** Python 3.12 + FastAPI + SQLAlchemy 2 + Alembic + Pydantic v2 (быстро, автогенерация OpenAPI). Альтернатива для «enterprise»-очков — Kotlin/Spring Boot, но дольше.
- **БД:** PostgreSQL 16.
- **Очередь/асинхронность:** Redis (+ RQ/Celery или arq) — конвейер проверок выполняется воркером, статусы двигаются асинхронно → реалистичность и отказоустойчивость.
- **Realtime:** SSE (или WebSocket) для динамического статуса и in-app уведомлений.
- **Frontend:** React + TypeScript + Vite, UI-кит (Mantine/AntD), TanStack Query. Два приложения в одном SPA с разными ролями: **Кабинет клиента** и **Рабочее место андеррайтера**.
- **Моки внешних систем:** отдельный сервис `mock-gateway` (FastAPI) — ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ, ЭП, платёжный шлюз. С настраиваемыми задержками и ошибками (для демонстрации retry/circuit breaker).
- **Хранение файлов:** MinIO (S3-совместимое).
- **Auth:** Keycloak (enterprise-плюс) или собственный JWT + RBAC (проще). Рекомендация: JWT + RBAC, Keycloak — если хватает времени.
- **LLM (опц.):** Ollama + Qwen2.5-7B-Instruct / Llama-3.1-8B (open weights), отключаемый флагом `LLM_ENABLED`, с fallback на шаблоны.
- **Наблюдаемость:** структурные JSON-логи, `/health`, `/metrics` (Prometheus) — минимум; Grafana опционально.
- **Reverse proxy:** nginx (раздаёт фронт, проксирует `/api`).

### Компоненты (docker-compose)
```
nginx ─┬─ frontend (static)
       └─ api (FastAPI) ── postgres
              │  └──────── redis ── worker (конвейер: проверки, скоринг, решение)
              │                         └── mock-gateway (ЕГРЮЛ, ФНС, БКИ, ЭП, платежи)
              └─ minio            └── ollama (profile "ai", опционально)
```

### Enterprise-аспекты (отдельный слайд + раздел README)
- Идемпотентность (`Idempotency-Key` на submit), оптимистичные блокировки (version в заявке).
- Transactional outbox для событий смены статуса; журнал событий (`application_events`) = аудит.
- Retry с backoff + таймауты + circuit breaker на интеграциях; деградация (БКИ недоступно → MANUAL_REVIEW, а не падение).
- RBAC, валидация на сервере, маскирование ПДн в логах, секреты через env, нет секретов в репо.
- Stateless API → горизонтальное масштабирование; воркеры масштабируются отдельно.
- Миграции Alembic, healthchecks в compose, тесты в CI (GitHub Actions: lint + tests + build).
- Версионирование правил скоринга (каждое решение хранит `ruleset_version` → воспроизводимость и объяснимость).

## 4. Скоринг и кредитное решение (ядро кейса)

Явно разделяем **скоринг (оценка риска)** и **кредитное решение (политика)** — это прямо подчёркнуто в кейсе.

### 4.1 Hard-stop правила (стоп-факторы)
- Компания ликвидирована/в процессе ликвидации (ЕГРЮЛ) → REJECTED.
- Возраст бизнеса < 3 мес (или < 6 мес для инвест. кредита) → REJECTED/иной продукт.
- Текущая просрочка > 30 дней в БКИ → REJECTED.
- Руководитель в реестре дисквалифицированных / массовый адрес (ФНС) → MANUAL_REVIEW.

### 4.2 Балльная скоринговая модель (scorecard)
Факторы с весами (пример, всё в конфиге YAML):
| Фактор | Пример баллов |
|---|---|
| Возраст бизнеса | <1 г: 0; 1–3 г: 20; >3 г: 40 |
| Выручка / тренд | падение >20%: −20; рост: +20 |
| Долговая нагрузка (DSCR / платежи к выручке) | >50%: −40; <20%: +30 |
| Кредитная история (БКИ) | просрочки в 12 мес: −30…−60; чистая: +30 |
| Отрасль (ОКВЭД) | рисковые: −15 |
| Обороты по счёту в банке | есть стабильные: +25 |
| Сумма заявки / годовая выручка | >50%: −30 |

Итог → **PD-подобный рейтинг** A/B/C/D/E и прозрачный разбор «какие факторы повлияли» (explainability — показываем и андеррайтеру, и клиенту в мягкой формулировке).

### 4.3 Decision engine (политика)
Вход: рейтинг + продукт + сумма/срок + стоп-факторы + лимиты.
- A/B, сумма ≤ автолимита продукта → **AUTO_APPROVED**.
- A/B, сумма > автолимита или C → **MANUAL_REVIEW**.
- Рейтинг позволяет меньший лимит → **COUNTER_OFFER** (макс. сумма = f(выручка, нагрузка), иной срок или другой продукт, напр. овердрафт вместо кредита).
- Нехватка данных → **NEEDS_INFO** с конкретным списком задач клиенту.
- D/E или стоп-фактор → **REJECTED** с объяснением и рекомендациями.
- Ставка = базовая ставка продукта + надбавка за рейтинг (риск-ориентированное ценообразование).

### 4.4 Продуктовая линейка (синтетика, 4–5 продуктов)
1. Экспресс-кредит на оборотку (до 5 млн, до 24 мес, без залога, автоматическое решение).
2. Овердрафт (до 30% оборотов).
3. Инвестиционный кредит (до 100 млн, до 7 лет, залог обязателен, всегда ручная проверка).
4. Кредит под госгарантию/МСП-корпорация (смоделировано) — опционально.
5. Кредитная бизнес-карта.

## 5. Функциональность (экраны)

### 5.1 Кабинет клиента (MUST)
1. **Вход** (тестовые учётки; выбор компании, если их несколько).
2. **Главная/дашборд:** активные заявки с прогресс-баром, задачи «что нужно сделать», предложения, **новостная лента**.
3. **Подбор продукта (мастер по цели):** «Для чего деньги?» (кассовый разрыв / закупка / оборудование / развитие / пополнение оборотки) + сумма + срок → 1–3 рекомендованных продукта с понятным сравнением, калькулятором платежа и **предварительной оценкой шанса одобрения** (pre-score без влияния на КИ).
4. **Анкета заявки (пошаговая, с автосохранением черновика):**
   - Компания — автозаполнение по ИНН из мока ЕГРЮЛ (снижает повторный ввод).
   - Финансы — предзаполнено из «данных банка», можно поправить.
   - Залог/поручители (только если требует продукт).
   - Документы — drag&drop, чек-лист, (опц.) OCR/распознавание.
   - Согласия (обработка ПДн, запрос в БКИ) — чекбоксы.
   - Проверка и отправка.
5. **Карточка заявки:** таймлайн статусов в реальном времени (SSE), человеческие пояснения каждого этапа («Проверяем данные в ЕГРЮЛ — обычно до 1 мин»), ожидаемое время, задачи от банка (NEEDS_INFO), чат с банком внутри продукта.
6. **Оффер/решение:** условия, график платежей, сравнение запрошенного vs предложенного, кнопки «Принять / Отказаться / Изменить параметры»; при отказе — понятные причины и что сделать.
7. **Подписание** (симуляция: подтверждение кодом, отображаемым в интерфейсе — не SMS) → **Выдача** (симуляция зачисления на счёт, баланс изменяется).
8. **Уведомления** — только in-app (колокольчик + SSE).

### 5.2 Рабочее место банка (MUST)
1. **Очередь заявок** с фильтрами (статус, продукт, SLA, рейтинг, сумма), SLA-подсветка.
2. **Карточка заявки андеррайтера:** анкета, результаты всех проверок (ЕГРЮЛ/ФНС/БКИ) с исходными ответами, скоринг с разбором факторов, стоп-факторы, документы, история событий/аудит.
3. **Действия:** одобрить / отказать / контрпредложение (изменить сумму/срок/продукт) / запросить информацию (создаёт задачу клиенту) / эскалировать на APPROVER. Обязательный комментарий, всё логируется.
4. **(SHOULD)** Админка: продукты, веса скоринга, лимиты (версионирование ruleset).
5. **(COULD)** Дашборд воронки: конверсия по этапам, time-to-decision, доля автоодобрений.

### 5.3 Персонализированная новостная лента (явное требование демо!)
Лента в кабинете клиента, меняется в зависимости от **профиля и состояния**:
- Источники: синтетический корпус новостей/материалов с тегами (`okved`, `segment`, `product`, `stage`, `region`, `event`).
- Правила ранжирования (rule-based + опционально эмбеддинги open-source, напр. `multilingual-e5-small`):
  - по отрасли (ОКВЭД): «Для общепита — изменения в маркировке», «Господдержка для производств»;
  - по стадии заявки: черновик → «Как подготовить отчётность»; NEEDS_INFO → «Какие документы нужны»; одобрено → «Как работает график платежей»; отказ → «Как улучшить кредитную историю»;
  - по размеру бизнеса/продуктам: акции на продукты, которые подходят по pre-score;
  - по событиям: налоговые сроки, изменения законодательства.
- Каждая карточка — с пометкой «Почему вы это видите» (прозрачность).
- **Демо-ход:** переключаем двух клиентов (кофейня vs производство) и/или двигаем заявку по статусам — лента заметно меняется.
- (Опц.) LLM делает краткое саммари новости под клиента.

## 6. Синтетические данные и тестовые учётки

- Сид-скрипт (`make seed` / автоматически при старте) с Faker(ru_RU) + детерминированный seed.
- **5–7 демо-компаний под ключевые ветки сценария** (обязательно!):
  | Учётка | Компания | Ожидаемый исход |
  |---|---|---|
  | `client_good` | ИП кофейня, 4 года, чистая КИ | AUTO_APPROVED |
  | `client_counter` | ООО торговля, высокая нагрузка | COUNTER_OFFER (меньше сумма) |
  | `client_info` | ООО без отчётности | NEEDS_INFO → догрузка → одобрение |
  | `client_manual` | ООО производство, инвест. кредит 40 млн | MANUAL_REVIEW |
  | `client_reject` | ИП с просрочкой 60 дней | REJECTED с объяснением |
  | `client_liquidated` | ООО в ликвидации | Hard-stop |
  | `underwriter`, `approver`, `admin` | — | банковские роли |
- Мок-ответы ЕГРЮЛ/ФНС/БКИ лежат в JSON-фикстурах по ИНН; для неизвестного ИНН — генерация.
- Корпус новостей: 40–60 синтетических статей с тегами.

## 7. ИИ — только там, где есть ценность (все модели — open weights)

| Фича | Ценность | Реализация | Приоритет |
|---|---|---|---|
| Ассистент-помощник по выбору продукта и терминам («что такое овердрафт», «почему мне предложили меньше») | снижает барьер для неэксперта | Ollama + Qwen2.5-7B, RAG по базе продуктов/FAQ, guardrails | SHOULD |
| Объяснение решения человеческим языком | прозрачность отказа/контроффера | шаблоны (MUST) + LLM-перефраз (COULD) | MUST/COULD |
| Распознавание документов (выписка/отчётность → поля) | меньше ручного ввода | Tesseract/PaddleOCR + парсинг; или подготовленные «машиночитаемые» PDF | COULD |
| Саммари заявки для андеррайтера | экономия времени | LLM по структурированным данным | COULD |
| Персонализация ленты | релевантность | правила + open-source эмбеддинги | MUST (правила) |

Всё ИИ отключаемо; без него основной сценарий работает полностью (жюри: «не заменяют работоспособность основного сценария»).

## 10. Демо-сценарий (5–7 минут)

1. Проблема и персоны (30 сек) → что в MVP и почему (MoSCoW).
2. Вход `client_good` → лента под кофейню → подбор по цели «закупка» → pre-score → заявка с автозаполнением по ИНН → отправка → **статус живьём** идёт по этапам → AUTO_APPROVED → оффер → подпись → выдача, баланс изменился.
3. `client_counter` → контрпредложение с объяснением.
4. `client_manual` → переключение на андеррайтера: очередь, разбор скоринга, «запросить документ» → у клиента in-app задача → догрузка → одобрение андеррайтером.
5. Смена клиента → **лента изменилась** (отрасль + стадия заявки), «почему вы это видите».
6. Enterprise-слайд: архитектура, отказ мока БКИ → заявка корректно уходит в ручную проверку (показать вживую).
7. Развитие: реальные интеграции, ML-скоринг на исторических данных, мониторинг стабильности модели, A/B правил.

## 11. Риски и как их снизить

| Риск | Митигация |
|---|---|
| Не успеть сквозной путь | сначала «тонкий» E2E (заявка → авто-решение → оффер) к концу 1-го дня, потом наращивать |
| LLM тяжёлая для ПК жюри | отдельный profile, маленькая модель, fallback на шаблоны |
| Интеграция фронт/бэк | OpenAPI-first, генерация TS-клиента (openapi-typescript) |
| Падение демо | облачный деплой + локальный + записанное видео |
| Формальное применение фреймворков | каждое решение в docs привязано к конкретной боли/метрике |

## 12. Приоритеты MoSCoW (итог)
